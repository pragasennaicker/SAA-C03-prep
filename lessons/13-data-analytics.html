01 · ARCHITECTURE DRAWING

Build stream into a lake, then query and warehouse

ARCHITECTURE

Producers

Clickstreams, IoT, and apps emit events. The first decision is replayable stream vs delivery stream.

ARCHITECTURE

Kinesis Data Streams

Replayable shards. Consumers can rewind. You manage (or on-demand) shard capacity.

ARCHITECTURE

Firehose

Fully managed delivery into S3, Redshift, OpenSearch. Near real-time, not sub-second analytics.

ARCHITECTURE

S3 data lake

The durable landing zone. Partition it; later engines query these objects.

ARCHITECTURE

Glue

Crawlers fill the Data Catalog. ETL jobs transform. Athena and Redshift Spectrum use that catalog.

ARCHITECTURE

Athena

Serverless SQL over S3. You pay for data scanned — Parquet and partition pruning matter.

ARCHITECTURE

Redshift

Columnar warehouse for heavy, repeated analytics. Not the same as Athena ad-hoc queries.

ARCHITECTURE

EMR

Managed Hadoop/Spark when you need a cluster and custom processing beyond Glue jobs.

ARCHITECTURE

The full analytics path

Producers → Kinesis → Firehose → S3. Glue catalogs. Athena queries the lake; Redshift warehouses; EMR is custom Spark/Hadoop.

02 · DEEP DIVE

What you actually need to understand

1

Kinesis Data Streams

  • Real-time streaming service for producers and multiple consumers.
  • Partition/shard key design determines distribution and ordering scope.
  • Use when applications need direct control over consuming/processing a stream.
  • Enhanced fan-out and scaling concepts matter at architecture level; avoid hot partitions.
2

Data Firehose

  • Managed delivery of streaming data to supported destinations such as S3, Redshift and OpenSearch.
  • Reduces operational work when the goal is delivery rather than custom stream-consumer control.
  • Can buffer and transform records before delivery.
  • Think 'streaming delivery pipe' rather than a general message queue.
3

S3 data lake + Glue

  • S3 is the durable data-lake storage layer.
  • Glue Data Catalog stores table/schema metadata for analytics services.
  • Glue ETL jobs transform datasets into query-friendly formats/partitions.
  • Lake Formation simplifies data-lake governance and permissions on top of lake resources.
4

Athena + Redshift

  • Athena performs serverless SQL queries on data in S3; cost is strongly influenced by data scanned, so columnar formats/partitioning help.
  • Redshift is a managed analytical data warehouse for repeated warehouse-style analytics.
  • Use Redshift Spectrum capabilities where appropriate to query data outside warehouse storage.
  • OLTP databases are not interchangeable with analytics warehouses.
5

EMR + OpenSearch + BI

  • EMR runs managed big-data frameworks such as Spark and Hadoop.
  • OpenSearch is useful for search, log analytics and near-real-time indexing/query patterns.
  • AWS's current in-scope analytics list also includes Amazon Quick for BI/analytics recognition.
  • Choose from processing/query pattern rather than dataset size alone.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Replayable telemetry stream

Constraint: several consumers need ordered device telemetry and must replay records after failures. Design: Kinesis Data Streams partitions by device and retains records for independent consumers. Why alternatives fail: Firehose is delivery-focused, and SQS does not provide the same shard-based replay stream.

1 Partition key preserves order→2 Consumers read independently→3 Retention enables replay
WORKED SCENARIO

Serverless log investigation

Constraint: analysts sporadically query years of logs in S3 without loading a warehouse. Design: catalog partitioned Parquet data with Glue and query it using Athena. Why alternatives fail: Redshift adds provisioned warehouse concerns, and RDS is not optimized for lake scans.

1 Athena queries S3→2 Glue supplies schema→3 Parquet reduces bytes scanned
WORKED SCENARIO

Repeated BI joins

Constraint: many users run frequent complex joins and aggregations over curated enterprise data. Design: load a dimensional model into Redshift and scale or isolate workloads appropriately. Why alternatives fail: Athena can be less predictable for repeated high-concurrency BI, and DynamoDB lacks relational joins.

1 Redshift is columnar→2 MPP accelerates analytics→3 Workload controls concurrency

06 · KNOWLEDGE CHECK

Twenty-five SAA-style questions

Q1A logistics company collects device telemetry from thousands of trucks. Several analytics applications must read the same records independently, preserve per-device order, and replay history after a consumer failure. The team will write custom consumer code and does not want a managed delivery pipe into a data store. Which solution will meet these requirements?
Answer: A. Independent custom consumers, per-device ordering, and replay are Amazon Kinesis Data Streams. Firehose is a managed delivery pipe, not a replayable consumer API.

Good to know: Firehose would be correct if the stem asked only to buffer, compress, and land files in S3, Redshift, or OpenSearch with almost no consumer code.
Q2A mobile studio publishes player events to Amazon Kinesis Data Streams. Events for one player must stay in write order, but different players may be processed in parallel. A previous design used a single constant partition key and overloaded one shard. The studio must avoid that hot-partition pattern. Which solution will meet these requirements?
Answer: C. The partition key chooses the shard and the ordering scope. A high-cardinality player key keeps one player ordered while spreading load; a constant key creates a hot partition.

Good to know: Firehose still batches for delivery; it does not give the same shard-level consumer control. Warehouse sort keys are for query layout, not stream ingest order.
Q3A media company wants clickstream records delivered into Amazon S3 as compressed objects for later lake analytics. Operations wants AWS to buffer, optionally transform, and load the files with almost no consumer application to maintain. The company does not want to manage stream shards. Sub-second processing of each record is not required. Which solution will meet these requirements?
Answer: B. Managed buffering, compression, optional transform, and delivery to S3 is Amazon Data Firehose. It is near real-time delivery, not a custom shard consumer.

Good to know: Kinesis Data Streams would win if several applications needed to rewind and process the same records with their own code. EMR is the Spark/Hadoop cluster answer, not a low-ops delivery pipe.
Q4An operations team must index application logs for search and near-real-time log analytics. Events arrive as a stream and should be delivered into the search service with buffering and little custom consumer code. The team does not need a general-purpose queue and will not query the logs with warehouse SQL as the primary interface. Which solution will meet these requirements?
Answer: D. OpenSearch is the search and log-analytics engine in this lesson. Firehose is the managed delivery path into OpenSearch when the goal is loading, not custom stream consumers.

Good to know: Athena on a partitioned S3 lake is the serverless SQL investigation pattern. Redshift is repeated warehouse analytics, not a search index.
Q5Producers emit order events that must land in Amazon S3 for a data lake. Developers asked for a general message queue so workers can delete each message after a job. Architects instead need a managed streaming delivery pipe that buffers and writes objects, not a queue and not custom shard consumers. Which solution will meet these requirements?
Answer: A. Firehose is a streaming delivery pipe to destinations such as S3, not a general-purpose queue and not a replayable consumer API.

Good to know: Kinesis Data Streams is the answer when the stem requires custom consumers and replay. Glue crawlers discover schemas; they do not replace ingest.
Q6Analysts must run SQL against years of objects in an Amazon S3 data lake. Several engines, including Amazon Athena, need a shared table and schema registry that crawlers can populate automatically. The company does not want to load a warehouse just to store metadata. Which solution will meet these requirements?
Answer: C. Glue crawlers infer schemas and fill the Glue Data Catalog, which Athena and Redshift Spectrum use as lake table metadata.

Good to know: Lake Formation then layers lake permissions on those cataloged resources. Redshift still needs Spectrum or an external schema to see S3 through the catalog.
Q7A data lake in Amazon S3 holds raw JSON extracts that are slow and expensive for Amazon Athena to scan. Pipelines must rewrite the datasets into a query-friendly columnar layout with partitions that match common filters. The team wants managed ETL rather than operating a long-lived Hadoop cluster. Which solution will meet these requirements?
Answer: B. Glue ETL is the managed transform path that writes query-friendly formats and partitions in the S3 lake. EMR is for custom Spark or Hadoop when you need a cluster beyond Glue jobs.

Good to know: Firehose can convert incoming streams on the way to S3, but this stem is a lake rewrite of objects that are already stored, which is Glue ETL.
Q8Several business units share an Amazon S3 data lake registered in the AWS Glue Data Catalog. Security wants a lake-focused permissions model on those cataloged databases and tables rather than relying only on individual bucket policies. Analysts will keep querying with Amazon Athena and will not move the lake into a warehouse just to control access. Which solution will meet these requirements?
Answer: D. Lake Formation is the lesson’s data-lake governance and permissions layer on top of lake resources that the Glue Data Catalog already describes.

Good to know: Bucket policies still matter for the objects, but they are not the catalog-aware lake permission model this stem asks for. Redshift WLM controls warehouse concurrency, not S3 lake grants.
Q9Investigators sporadically query years of application logs that already live in Amazon S3. They need SQL without provisioning a warehouse cluster and without loading the logs into a database first. Queries are occasional, so paying for data scanned is acceptable if the lake stays in S3. Which solution will meet these requirements?
Answer: A. Athena is serverless SQL on S3. Cost follows data scanned, which fits sporadic investigation. Redshift is the provisioned warehouse for repeated heavy BI.

Good to know: OpenSearch is search and log analytics with an index model, not the serverless lake-SQL answer. EMR fits custom Spark or Hadoop processing beyond Glue jobs.
Q10Analysts already use Amazon Athena against JSON logs in Amazon S3. Queries filter on event date but still scan entire prefixes, and the bill tracks data scanned. The company will keep Athena, will not load a warehouse, and wants the same SQL to read less data. Which solution will meet these requirements MOST cost-effectively?
Answer: C. Athena charges by data scanned. Columnar Parquet reads needed columns, and date partitions let Athena skip files outside the filter.

Good to know: Redshift would appear if the stem demanded frequent high-concurrency warehouse joins. Extra Regions and extra Kinesis shards do not change Athena scan bytes.
Q11Many analysts run frequent complex joins and aggregations over terabytes of curated enterprise data throughout the day. The company needs a columnar massively parallel warehouse rather than ad-hoc scans of a raw S3 lake. Interactive search of application logs is not the requirement, and an OLTP database is not the analytics engine. Which solution will meet these requirements?
Answer: B. Repeated warehouse-style joins and aggregations are Amazon Redshift’s columnar MPP pattern. Athena is serverless SQL on S3 and is less the exam answer for heavy all-day BI.

Good to know: Athena remains the better fit when queries are sporadic and the data should stay in the lake. OpenSearch is search and log analytics, not a relational warehouse.
Q12A company already runs Amazon Redshift for dimensional analytics. Several large fact extracts remain in Amazon S3 and are registered in the AWS Glue Data Catalog. Analysts must join warehouse tables with those files without loading every object into Redshift local storage. Copying the entire lake into the cluster is too slow and costly. Which solution will meet these requirements?
Answer: D. Redshift Spectrum queries data that lives outside warehouse storage, typically in S3, using catalog metadata Glue already holds.

Good to know: Athena would be the answer if there were no warehouse and the only need was serverless SQL on S3. Loading into Redshift is valid when the stem wants data inside the cluster.
Q13A genomics pipeline needs Apache Spark and Hadoop jobs with custom libraries that go beyond AWS Glue ETL. Input datasets already sit in an Amazon S3 data lake. The team wants a managed cluster for those frameworks rather than building Hadoop on unmanaged Amazon EC2. Which solution will meet these requirements?
Answer: A. EMR is the managed Spark and Hadoop service when processing goes beyond Glue jobs or Athena SQL. The S3 lake remains the durable store.

Good to know: Glue ETL is the lower-ops transform when Spark custom libraries are not required. Athena is serverless SQL, not a general Spark runtime.
Q14A support organization must search free-text ticket comments and run near-real-time log analytics on operational events. Users need an index and search model rather than serverless SQL over an S3 lake or a columnar warehouse. The company will not operate self-managed search clusters and rejected Amazon Athena as the primary search interface. Which solution will meet these requirements?
Answer: C. OpenSearch is the lesson’s search and log-analytics service. Athena and Redshift are SQL over lakes or warehouses, not a search index.

Good to know: Firehose is a common managed path into OpenSearch when the source is a stream. Glue Data Catalog stores table schemas, not a full-text search corpus.
Q15A finance team already queries curated tables in Amazon Redshift. Business users need interactive dashboards and visuals without writing SQL for every request. The company wants a BI service rather than a search cluster, a Spark job, or another warehouse. The curated Redshift tables remain the source for the visuals. Which solution will meet these requirements?
Answer: B. Amazon QuickSight is the BI service for dashboards and visuals. OpenSearch, EMR, and Firehose solve search, Spark processing, and stream delivery, not BI authoring.

Good to know: Athena can also feed QuickSight when the stem is lake SQL rather than a warehouse. Do not treat a lesson mention of Amazon Quick as a different product name.
Q16Batch extracts and streaming landings must be stored so Amazon Athena, Amazon Redshift Spectrum, and Amazon EMR can all read the same objects later. The company wants durable object storage as the system of record, not a provisioned warehouse and not a time-bounded stream. Which solution will meet these requirements?
Answer: D. S3 is the durable data-lake landing zone. Later engines query those objects after Glue catalogs them. Streams and warehouses are not the shared lake.

Good to know: Partition the lake and convert to columnar formats so Athena scan cost stays predictable. Redshift is for curated warehouse analytics on top of, not instead of, the lake when multiple engines must share files.
Q17Clickstream producers already write to Amazon Kinesis Data Streams. A new requirement is to land compressed files in Amazon S3 for the lake with minimal new consumer code. Existing custom consumers must keep reading the same stream for real-time processing. Which solution will meet these requirements with the LEAST operational overhead for the S3 path?
Answer: A. Firehose is the low-ops delivery path to S3. Kinesis Data Streams can still feed custom consumers; Firehose handles buffering and object writes.

Good to know: If no custom consumers existed, producers could send to Firehose directly. Warehouse UNLOAD is not the managed stream-to-lake pattern.
Q18A company already uses Amazon Redshift for BI. Streaming click events from producers must be buffered, compressed, and loaded into that warehouse. Operations will not write custom Kinesis consumers or manage shard capacity, and sub-second per-record analytics is not required. The warehouse remains the destination of record. Which solution will meet these requirements?
Answer: C. Firehose supports managed delivery into Redshift with buffering and compression. That is delivery, not custom stream processing.

Good to know: Kinesis Data Streams would be required if independent applications needed to replay the events. OpenSearch is not a columnar MPP warehouse.
Q19Amazon Athena queries against a JSON data lake in Amazon S3 scan too much data and cost too much. Analysts filter on date and a small set of columns. The company will keep Athena and the S3 lake and will not provision a warehouse for this workload. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and C. Parquet lets Athena read needed columns, and partitions skip files outside common predicates. Those two layout changes are the direct scan-cost levers.

Good to know: Redshift nodes do not serve Athena. Extra Kinesis shards change ingest capacity, not lake scan bytes.
Q20IoT devices emit telemetry that several applications must consume in per-device order. After a consumer outage, each application must replay recent records independently. The team will write custom consumers and will not use a managed delivery stream as the only ingest path. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and D. Kinesis Data Streams plus a device partition key gives per-device order on a shard. Retention is what lets independent consumers rewind after failures.

Good to know: Firehose would be correct if the only goal were buffered delivery to S3, Redshift, or OpenSearch. Lake Formation governs lake permissions, not stream shards.
Q21Security analysts sporadically run SQL over years of logs in Amazon S3 and must not load a warehouse. Table schemas should be discovered and shared so Athena can query the objects. The company wants serverless SQL on the lake. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: C and E. Glue supplies the shared schema registry; Athena runs serverless SQL on S3. Together they are the sporadic lake-investigation pattern.

Good to know: Redshift is the answer when many users run frequent complex warehouse joins. OpenSearch is search and log analytics, not Athena’s lake SQL.
Q22A retailer must land streaming click events in Amazon S3 for a data lake with almost no consumer code. Records should be buffered, compressed, and optionally transformed before objects are written. The team does not need custom rewindable consumers for this path. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and E. Firehose is the managed delivery stream to S3. Buffering, compression, and transform are the operational features that remove custom consumer work.

Good to know: Kinesis Data Streams is the custom-consumer and replay answer. Spectrum queries S3 from Redshift; it does not ingest a live Kinesis stream.
Q23Raw files already sit in an Amazon S3 data lake. Pipelines must rewrite them into partitioned columnar objects, and Amazon Athena must see the new tables. The team wants managed ETL and a catalog rather than a long-lived Hadoop cluster. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and C. Glue ETL produces the query-friendly lake layout. The Glue Data Catalog is the schema registry Athena uses to find those tables.

Good to know: EMR would appear if the stem required custom Spark or Hadoop libraries beyond Glue jobs. Lake Formation would appear if the deciding constraint were lake permissions.
Q24A company already has curated tables in Amazon Redshift and a large Amazon S3 data lake registered in the AWS Glue Data Catalog. Analysts must run frequent complex joins on the warehouse tables and must also join those results with lake files they do not want to load. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: D and E. Redshift is the columnar MPP warehouse for repeated joins. Spectrum reaches S3 data that stays outside local warehouse storage, using the catalog.

Good to know: Athena alone would be correct if there were no warehouse and queries were sporadic lake SQL. OpenSearch does not replace warehouse joins.
Q25A research team needs Apache Spark jobs with custom libraries that AWS Glue ETL does not cover. Input datasets already live in an Amazon S3 data lake. The team wants a managed Spark and Hadoop platform rather than self-managed clusters on Amazon EC2. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and B. EMR supplies managed Spark and Hadoop. The S3 lake is the durable input the lesson already treats as the landing zone for later engines.

Good to know: Glue ETL remains the answer when transform and partition jobs do not need a custom Spark cluster. Athena is serverless SQL, not a Spark runtime.
