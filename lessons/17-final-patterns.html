01 · VISUAL MODEL

See the architecture before memorising the services

Diagram cue: Underline MUST / least ops / RTO / private / no code changes — eliminate violators before comparing cost.
①Translate words into constraints

Underline availability, durability, latency, throughput, recovery, operations, security, and cost requirements before selecting any service.

②Build the data path

Sketch entry, identity, compute, state, asynchronous boundaries, observability, and failure destinations; then test every hop against the stated constraints.

③Eliminate by violated requirement

Reject answers that break an explicit constraint, add unrequested operations, confuse authentication with authorization, or optimize a secondary concern.

④Prefer reversible decisions

When two answers work, favor managed, loosely coupled, multi-AZ, observable designs that scale independently and minimize undifferentiated operations.

02 · DEEP DIVE

What you actually need to understand

1

Classic three-tier web

  • Route 53/CloudFront → ALB → private application tier → relational database.
  • ASG spans AZs; database uses Multi-AZ where HA is required.
  • Security Groups reference tiers rather than opening broad CIDRs.
  • Static assets go to S3/CloudFront; ElastiCache can offload hot reads.
  • Secrets Manager/KMS/CloudWatch complete security/operations concerns.
2

Serverless API

  • CloudFront or front end → API Gateway → Lambda → DynamoDB/S3.
  • Cognito handles end-user identity.
  • SQS/EventBridge decouple asynchronous work.
  • Serverless services scale independently and reduce infrastructure management.
  • Use RDS Proxy if a relational DB is required behind high Lambda concurrency.
3

Event-driven microservices

  • Publish domain events instead of making every service synchronously call every other service.
  • Use SNS/EventBridge for routing/fanout and SQS per consumer for durable buffering.
  • DLQs isolate failures; idempotency protects against duplicate delivery.
  • Each service owns its scaling and failure domain.
4

Hybrid enterprise

  • On-premises → VPN or Direct Connect → Transit Gateway → multiple VPCs.
  • Centralized inspection/shared services can be attached to the hub.
  • Organizations/Control Tower/IAM Identity Center govern accounts and workforce access.
  • PrivateLink exposes selected services without broad network routing.
5

Exam method

  • 1. Identify the workload and architecture family.
  • 2. Underline hard constraints: MUST be private, RTO, protocol, no code changes, least ops, most cost-effective.
  • 3. Eliminate answers that violate any hard constraint.
  • 4. Compare the remaining answers on operations, resilience and cost.
  • 5. Flag lengthy questions and return; never leave an answer blank.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Resilient web transaction

Constraint: a public workload must remain available through an AZ failure and absorb bursts. Design: Route 53 and an ALB front Auto Scaling instances across AZs, with Multi-AZ data and SQS for asynchronous work. Why alternatives fail: one large instance is a single failure domain, and synchronous chaining spreads failure.

1 Multi-AZ removes one fault →2 Auto Scaling replaces capacity →3 Queues isolate bursts
WORKED SCENARIO

Choosing DR by objective

Constraint: the business supplies strict RTO and RPO rather than asking for maximum availability at any cost. Design: map backup/restore, pilot light, warm standby, or multi-site to those objectives and test recovery. Why alternatives fail: backups may miss a short RTO, while active-active can overspend for relaxed objectives.

1 RPO limits lost data →2 RTO limits outage →3 Testing validates recovery
WORKED SCENARIO

Resolving two plausible answers

Constraint: two architectures appear technically possible under time pressure. Design: compare each against every superlative and explicit constraint, then choose the simplest managed option satisfying all. Why alternatives fail: keyword matching ignores trade-offs, and adding services can violate cost or operations requirements.

1 Read the final ask →2 Honor every constraint →3 Managed usually lowers ops
05 · EXAM LANGUAGE DECODER

Words in the question that should trigger a design instinct

“least operational overhead”
→ Prefer managed/serverless among otherwise valid answers.
“without modifying application”
→ Look for infrastructure/proxy/migration-layer solution.
“most cost-effective”
→ Do not violate resilience/security just to be cheap.
“millions of requests + unpredictable”
→ Elastic/serverless patterns.
“decouple components”
→ Queues/events.
“single point of failure”
→ Spread across AZs / managed HA.
06 · KNOWLEDGE CHECK

Five SAA-style questions

Q1A question asks for the least operationally intensive highly available relational database. Which clue should dominate when several technically valid designs appear?
Answer: A. The explicit superlative is decisive: a managed Multi-AZ database generally minimizes administration while meeting availability.
Q2A workload can tolerate hours of recovery and up to one day of data loss. Which disaster-recovery strategy is usually the most cost-effective starting point?
Answer: A. Relaxed RTO and RPO commonly permit backup and restore, which has lower steady-state cost than continuously running environments.
Q3An order API must respond quickly even when fulfillment is slow or unavailable. Which general architecture pattern best isolates the user request path?
Answer: A. A durable queue decouples availability and rate, allowing the API to acknowledge accepted work without waiting for fulfillment.
Q4Two answers meet functional needs, but one uses self-managed clusters and the other a managed service with equivalent controls. The stem says minimize operations. Choose what?
Answer: A. When constraints are otherwise equal, the managed service directly satisfies the requirement to minimize operational overhead.
Q5A design is Multi-AZ but has synchronous dependencies on one regional external endpoint. What exam habit most likely reveals this hidden availability risk?
Answer: A. End-to-end tracing exposes dependencies whose failure can defeat otherwise redundant compute and storage layers.
