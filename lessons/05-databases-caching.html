01 · ARCHITECTURE DRAWING

Build relational HA plus a purpose-built store

ARCHITECTURE

VPC

Keep the relational writer in private subnets across AZs. Purpose-built stores sit beside it, not as replicas of it.

ARCHITECTURE

App tier

The application chooses the data store. Caching and DynamoDB are extra paths, not drop-in RDS replicas.

ARCHITECTURE

ElastiCache

Sub-millisecond cache. It is not a database, not durable storage, and not a Multi-AZ failover strategy by itself.

ARCHITECTURE

Aurora Multi-AZ

The writer is protected by Multi-AZ. Readers scale reads. A replica is not a different data model.

ARCHITECTURE

DynamoDB

A key-value / document store with its own partition-key design. It is not an Aurora replica.

ARCHITECTURE

The full data path

The app reads the cache first, writes Aurora, and uses DynamoDB when the access pattern is key-value rather than SQL.

02 · DEEP DIVE

What you actually need to understand

1

RDS availability vs scaling

  • Multi-AZ creates a highly available deployment/failover architecture; it is not primarily a read-scaling feature.
  • Read replicas offload read traffic and may be cross-Region depending on engine/features.
  • RDS Proxy pools/manages DB connections and can protect relational databases from connection storms.
  • Automated backups/snapshots serve recovery needs; retention and cross-Region/cross-account strategy depend on requirements.
2

Aurora

  • Aurora uses distributed storage across Availability Zones and separates storage from database compute.
  • Aurora Replicas can scale reads and participate in failover.
  • Aurora Serverless variants fit variable or intermittent relational workloads where elastic database capacity is useful.
  • Global Database patterns support cross-Region read/locality and DR scenarios.
3

DynamoDB

  • Key-value/document model designed around partition and sort keys.
  • Choose partition keys that distribute traffic; poor keys create hot partitions.
  • On-demand capacity simplifies unpredictable traffic; provisioned capacity can be economical for predictable workloads.
  • Global Tables provide multi-Region active-active style replication.
  • DAX is an in-memory cache purpose-built for DynamoDB; TTL and Streams support lifecycle/event patterns.
4

Caching

  • ElastiCache reduces latency and database load for hot/repeated data.
  • Cache-aside is a common pattern: app checks cache, falls back to DB, then populates cache.
  • Use TTL/invalidation carefully so stale data remains acceptable.
  • Redis/Valkey-style capabilities suit richer data structures, replication and persistence options; Memcached is simpler distributed caching.
5

Purpose-built DBs

  • Neptune = graph relationships.
  • DocumentDB = MongoDB-compatible document use cases.
  • Keyspaces = Cassandra-compatible wide-column patterns.
  • Redshift = analytical warehouse, not OLTP.
  • Choose purpose-built services from the query/access pattern rather than trying to force every workload into one database.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Fail over a transactional database

An order system needs SQL transactions and automatic in-Region failover without application-managed replication. Use RDS Multi-AZ or an Aurora cluster across AZs. A read replica is primarily asynchronous read scaling and may lose recent changes, while DynamoDB requires a data-model rewrite.

1 SQL transactions→2 Synchronous HA→3 Managed failover
WORKED SCENARIO

Serve active-active user state

Users in multiple Regions need local, low-latency key-value writes with managed multi-Region replication. Use DynamoDB global tables and design conflict-tolerant access patterns. Cross-Region RDS replicas are not active-active writers, and ElastiCache is not the durable source of truth.

1 Local writes→2 Multi-Region→3 Managed replication
WORKED SCENARIO

Absorb repeated hot queries

A read-heavy application repeatedly requests the same database records and can tolerate brief cache staleness. Add ElastiCache using cache-aside with expiration and invalidation. More Multi-AZ standbys do not serve application reads, while scaling the writer alone wastes database resources.

1 Sub-ms reads→2 Offload database→3 Staleness allowed
05 · EXAM LANGUAGE DECODER

Words in the question that should trigger a design instinct

→ Multi-AZ.

→ Read replica.
“connection pooling for Lambda”
→ RDS Proxy.

→ DynamoDB.
“graph relationships”
→ Neptune.
“data warehouse / analytics SQL”
→ Redshift.
06 · KNOWLEDGE CHECK

Twenty-five SAA-style questions

Q1A retailer runs an order-entry application on Amazon EC2 that writes to a single-AZ Amazon RDS for PostgreSQL instance in private subnets. The application needs SQL transactions and automatic failover if the primary Availability Zone fails. Reporting queries can wait, and the team does not need extra read capacity. The company will not rewrite the schema. Which solution will meet these requirements?
Answer: A. In-Region relational high availability with automatic failover is RDS Multi-AZ. A read replica is asynchronous read scaling and is not the synchronous standby pattern.

Good to know: A read replica would be the answer if the stem demanded extra read capacity and accepted replica lag. DynamoDB global tables fit active-active key-value, not this SQL writer.
Q2A media site uses Amazon RDS for MySQL as the system of record. Editors write infrequently, but the public website issues many identical SELECT queries. The application can tolerate a few seconds of replica lag. Failover to a standby is already configured and is not the gap. Operators must not rewrite the application onto a NoSQL store. Which solution will meet these requirements?
Answer: C. Read scaling with tolerated lag selects RDS read replicas. Multi-AZ is already present for failover and does not offload application reads.

Good to know: Another Multi-AZ standby would matter if the gap were availability rather than read throughput. Redshift is a warehouse, not the OLTP read scaler.
Q3A company invokes thousands of AWS Lambda functions that open short-lived connections to Amazon RDS for PostgreSQL. During traffic spikes the database exhausts its connection limit and new functions fail. The team must keep the relational schema and must not replace RDS with a NoSQL store. Connection pooling should sit between Lambda and the database. Which solution will meet these requirements?
Answer: B. Lambda connection storms against a relational engine are the RDS Proxy pooling pattern. Multi-AZ failover does not multiplex application connections.

Good to know: Multi-AZ would be the answer if the stem asked for in-Region writer failover. DynamoDB would fit if the team were willing to abandon SQL.
Q4A SaaS vendor wants a MySQL-compatible relational database whose storage automatically replicates across Availability Zones and is decoupled from database compute. The application needs a managed writer with fast failover in one Region. The team does not want to operate shared storage on Amazon EC2. An analytics warehouse is out of scope. Which solution will meet these requirements?
Answer: D. Aurora separates compute from distributed storage that spans Availability Zones. That is the managed relational cluster the stem describes.

Good to know: Redshift would be correct for warehouse analytics SQL, not OLTP. ElastiCache is an in-memory cache, not durable relational storage.
Q5An Amazon Aurora PostgreSQL cluster has a single writer that is CPU-bound from reporting SELECTs. The application can send reads to other endpoints and can tolerate brief replica lag. The company also wants those readers to be eligible for failover if the writer fails. The workload must stay relational and in one Region. Which solution will meet these requirements?
Answer: A. Aurora Replicas offload reads and can participate in failover. That pair of constraints is the Aurora reader pattern, not a second unrelated RDS instance.

Good to know: ElastiCache would be the answer if the stem allowed cache-aside staleness in front of the writer without extra Aurora readers. Global tables are key-value active-active, not SQL reporting replicas.
Q6A department runs a MySQL-compatible reporting database that is idle most nights and then spikes for a few hours when analysts connect. The team wants elastic relational capacity without resizing instance classes by hand. The data model stays SQL. The workload is not a key-value store and is not a data warehouse. Which solution will meet these requirements?
Answer: C. Variable or intermittent relational load is the Aurora Serverless fit. DynamoDB on-demand is elastic, but it is not a SQL reporting engine.

Good to know: DynamoDB on-demand would be correct if the access pattern were key-value with unknown traffic. A peak-sized RDS instance would work if idle-time elasticity were not required.
Q7A ticketing platform uses Amazon Aurora in the US East (N. Virginia) Region. Customers in Europe need local low-latency reads of the same relational data, and operators want a managed way to promote a second Region for disaster recovery. Writes remain in one primary Region. The team will not rewrite the application onto key-value APIs. Which solution will meet these requirements?
Answer: B. Cross-Region relational reads, locality, and managed DR promotion are Aurora Global Database. Multi-AZ stays in one Region and does not place readers in Europe.

Good to know: DynamoDB global tables would be the answer for active-active key-value writes in both Regions. Multi-AZ would win if the only need were in-Region failover.
Q8A mobile game stores player inventories as items accessed by a known user identifier. Traffic is expected to reach very large request rates with single-digit millisecond reads and writes. The team does not want to manage database servers and does not need SQL joins. Graph traversal is not required. Which solution will meet these requirements?
Answer: D. Key-based access at huge scale with no server management is DynamoDB. RDS and Redshift are SQL engines; Neptune is a graph store.

Good to know: RDS would be correct if the stem required SQL transactions and joins. Neptune would win if the queries were multi-hop relationship traversals.
Q9A company stores session records in Amazon DynamoDB. The partition key is a status flag with only three values, so almost all traffic hits a few partitions and requests throttle. Access remains by key rather than SQL joins. The team must spread traffic across partitions and will not migrate the table to Amazon RDS. Which solution will meet these requirements?
Answer: A. Hot partitions come from a poorly distributed partition key. Changing capacity mode does not fix a key that concentrates traffic.

Good to know: On-demand capacity would be the answer if traffic volume were unknown but keys already spread evenly. RDS Proxy pools relational connections, not DynamoDB partitions.
Q10A new social feature writes to Amazon DynamoDB. Traffic is spiky and unknown for the first quarter, so the team cannot forecast read and write capacity units. Operators want AWS to handle capacity without a provisioning plan. After traffic becomes steady they may revisit cost. The access pattern stays key-value. Which solution will meet these requirements?
Answer: C. Unpredictable key-value traffic is on-demand capacity. A tiny provisioned ceiling will throttle spikes the team cannot forecast.

Good to know: Provisioned capacity (often with autoscaling) would be the economical answer if traffic were already predictable. ElastiCache is not the durable system of record.
Q11Users in two AWS Regions must read and write the same player profiles with locally low latency. The data is key-value, and the application can tolerate last-writer conflict handling. The company wants managed multi-Region replication rather than application-managed dual writes. Cross-Region RDS replicas are considered too write-constrained. Which solution will meet these requirements?
Answer: B. Managed multi-Region active-active key-value writes are DynamoDB global tables. An RDS replica is not an active-active writer.

Good to know: Aurora Global Database would be the answer for relational reads and DR in a second Region with one primary writer. RDS replicas scale reads, including cross-Region, with lag.
Q12An ecommerce API reads the same Amazon DynamoDB product items thousands of times per second and needs microsecond in-memory latency. The team wants a cache purpose-built for DynamoDB rather than a generic Redis client. Brief staleness is acceptable. The table must remain the durable system of record. Which solution will meet these requirements?
Answer: D. Microsecond caching that is purpose-built for DynamoDB is DAX. The table stays the system of record; DAX is not a warehouse or an RDS replica.

Good to know: ElastiCache cache-aside would be the answer for hot RDS (or generic) queries with tolerated staleness. DAX is the DynamoDB-specific cache.
Q13A catalog service on Amazon EC2 queries Amazon RDS for PostgreSQL for product pages. The same rows are requested repeatedly, the database CPU is high, and the application can tolerate a few seconds of stale data. The team will keep RDS as the source of truth and will not replace it with DynamoDB. Which solution will meet these requirements?
Answer: A. Repeated RDS reads with accepted staleness are ElastiCache cache-aside plus TTL. Extra Multi-AZ standbys do not serve those application reads.

Good to know: Read replicas would be correct if the stem wanted SQL read offload with lag instead of an in-memory cache. DAX is the DynamoDB cache, not an RDS feature.
Q14A gaming platform needs an in-memory cache for leaderboards and session state. The cache must support replication, optional persistence, and rich structures such as sorted sets. The team will use Amazon ElastiCache rather than a self-managed cluster on Amazon EC2. Amazon RDS remains the durable store for purchases. Which solution will meet these requirements?
Answer: C. Redis/Valkey-style ElastiCache provides richer structures, replication, and persistence options. Memcached is the simpler distributed cache.

Good to know: Memcached would be the answer if the stem wanted a simple distributed cache without those richer features. RDS is the durable OLTP store, not the in-memory leaderboard cache.
Q15A fraud team must query how accounts, devices, and payments are connected through many hops. The application issues graph traversals, not SQL joins or key-value GetItem calls. The team wants a managed graph database and will not force the model into Amazon RDS or Amazon DynamoDB. Which solution will meet these requirements?
Answer: B. Graph relationship traversals select Amazon Neptune. DynamoDB and RDS are the wrong data models for multi-hop graph queries.

Good to know: DynamoDB would be correct for key-value lookups by a known partition key. Redshift would win for warehouse analytics SQL, not graph hops.
Q16A product team already uses MongoDB APIs and drivers for a document catalog. They want a managed AWS database that remains MongoDB-compatible rather than rewriting queries to SQL or to the DynamoDB API. The workload is operational documents, not analytics SQL and not a graph of hops. Which solution will meet these requirements?
Answer: D. MongoDB-compatible document workloads map to Amazon DocumentDB. RDS and Redshift are SQL; Neptune is graph.

Good to know: DynamoDB would appear if the team were willing to adopt that API and key design. RDS would be correct if they were ready to rewrite to relational SQL.
Q17Developers run a wide-column application that speaks Apache Cassandra Query Language. They want a managed AWS service that stays Cassandra-compatible so they do not rewrite the data model for SQL or for DynamoDB. The access pattern is wide-column, not graph traversal and not a warehouse. Which solution will meet these requirements?
Answer: A. Cassandra-compatible wide-column access is Amazon Keyspaces. RDS is SQL, Neptune is graph, and Redshift is a warehouse.

Good to know: DynamoDB would be the answer if the team could redesign around partition and sort keys instead of CQL. DocumentDB would win for MongoDB APIs.
Q18Analysts need to run complex SQL aggregations over years of order history for dashboards. The current Amazon RDS instance slows down when those queries run. The company wants a columnar data warehouse, not another OLTP writer, and will not use a graph database. Nightly loads from RDS are acceptable. Which solution will meet these requirements?
Answer: C. Analytics SQL over large history is Amazon Redshift, not another OLTP system. ElastiCache and DAX are caches, not warehouses.

Good to know: Keeping the queries on RDS (or Aurora) with replicas would be the answer if the stem still wanted OLTP reporting rather than a warehouse. Neptune is for graph traversals.
Q19A payments API uses Amazon RDS for MySQL in one Region. The company needs automatic failover if the writer Availability Zone fails, and a reporting fleet must offload SELECTs. Reporting can tolerate replica lag. The application must keep SQL transactions and must not use the Multi-AZ standby as a read replica. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and C. In-Region HA and read offload are different controls: Multi-AZ for failover, read replicas for lag-tolerant SELECTs. The standby is not the read scaler.

Good to know: Querying the Multi-AZ standby would look right if Multi-AZ were taught as read scaling. ElastiCache is a cache, not the transactional ledger.
Q20AWS Lambda functions open a new database connection on every invoke against Amazon RDS for MySQL. During campaigns the instance hits its connection limit. The schema must stay relational. The team will not cache writes in Amazon ElastiCache as the source of truth. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and D. RDS Proxy must exist and the functions must connect through it so connections are pooled. Multi-AZ does not provide that pooling layer.

Good to know: DynamoDB would be correct if the team dropped SQL. Multi-AZ would be correct if the stem were about writer failover rather than connection storms.
Q21A retailer uses Amazon Aurora in one Region and must serve read-heavy storefront traffic from a second Region with a managed relational replica. Operators also need a documented path to promote the second Region during a regional event. The application stays SQL. Active-active key-value writes are not required. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: C and E. Aurora Global Database plus a secondary Region supplies cross-Region reads, locality, and a promotion path for DR. Those two steps are jointly required.

Good to know: DynamoDB global tables would be the answer for active-active key-value. Primary-Region Multi-AZ alone does not place relational readers in the second Region.
Q22A social app needs active-active key-value reads and writes in two Regions with managed replication. Poor key design already caused throttling in one Region. The team will not use Aurora Global Database as an active-active writer pair and will not store profiles only in ElastiCache. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and E. Global tables provide the managed active-active key-value fabric; even key design is still required so partitions do not overheat.

Good to know: An RDS cross-Region replica would be the answer for lag-tolerant SQL reads in a second Region, not active-active writes. RDS Proxy does not sit in front of DynamoDB.
Q23A news site on Amazon EC2 reads the same Amazon RDS rows for every homepage request. Database CPU is high. Editors accept that headlines may be up to 30 seconds stale. RDS must remain the durable store. The team will not enable DAX against RDS. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and C. Cache-aside plus TTL is how ElastiCache absorbs repeated RDS reads while keeping staleness within the allowed window.

Good to know: DAX would be the answer if the hot keys lived in DynamoDB. Extra Multi-AZ standbys still do not serve homepage reads.
Q24A high-traffic API uses Amazon DynamoDB as the only database. Repeated GetItem calls for the same keys dominate read capacity. The team wants a DynamoDB-specific in-memory cache and must keep the table as the system of record. Generic Redis in front of RDS is out of scope. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: D and E. DAX must be enabled and the application must send DynamoDB reads through it. The table remains durable storage behind the cache.

Good to know: ElastiCache as the database would violate the system-of-record constraint. ElastiCache cache-aside would be correct for hot RDS queries.
Q25A company stores device telemetry in Amazon DynamoDB. Items should disappear after 90 days without a cleanup fleet, and a downstream AWS Lambda function must react to new inserts. The team will not run a nightly Amazon RDS copy job. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and B. TTL expires items without a sweeper fleet. Streams deliver change events so Lambda can react to inserts. Those features are independent and both required here.

Good to know: A scheduled copy into RDS would be a different, heavier lifecycle design. ElastiCache alone is not durable telemetry storage.
