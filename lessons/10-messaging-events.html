01 · VISUAL MODEL

See the architecture before memorising the services

Diagram cue: Fan-out with SNS/EventBridge; buffer with SQS; isolate failures with a DLQ and idempotent consumers.
①Name delivery semantics

Label queues and buses with ordering, duplication, retention, retry, and acknowledgement behavior. Standard SQS is at-least-once; FIFO adds ordered message groups and deduplication.

②Distinguish queue from fan-out

Use SQS when consumers pull and buffer work, SNS when publishers push one message to many subscribers, and combine them for durable fan-out.

③Map event intent

EventBridge routes application and SaaS events by content; Step Functions coordinates stateful workflows, branching, retries, waits, and compensation.

④Place failure stores deliberately

Draw source-queue DLQs, subscription redrive, EventBridge DLQs, and workflow catches at the component that owns retry exhaustion.

02 · DEEP DIVE

What you actually need to understand

1

SQS

  • Queue decouples producers and consumers and absorbs bursts.
  • Standard queues prioritize scale and at-least-once delivery; consumers should be idempotent.
  • FIFO queues add ordering and deduplication semantics for workloads that require them.
  • Visibility timeout prevents another consumer from immediately processing an in-flight message.
  • Dead-letter queues isolate repeatedly failing messages for investigation/replay.
2

SNS

  • Topic-based pub/sub fanout to multiple subscribers.
  • A strong pattern is SNS → separate SQS queues per downstream service, so each consumer owns its backlog/retries.
  • Can deliver to supported endpoints such as SQS, Lambda and notifications.
  • Filtering can reduce unnecessary deliveries to subscribers.
3

EventBridge

  • Event bus routes events using rules/patterns.
  • Useful for AWS service events, custom domain events and SaaS integrations.
  • Decouples event producers from consumers without each producer knowing every destination.
  • Schedules are available through EventBridge scheduling capabilities, but distinguish event routing from durable work queues.
4

Step Functions

  • State-machine orchestration for multi-step workflows.
  • Handles branching, retries, waiting and error paths explicitly.
  • Useful when business process state must be visible and coordinated.
  • Contrast choreography (events between services) with orchestration (central workflow).
5

Amazon MQ + integration

  • Amazon MQ supports familiar broker protocols/engines for migrations requiring traditional messaging compatibility.
  • AppFlow handles managed data transfer between supported SaaS and AWS services.
  • Choose purpose-built native services when protocol compatibility is not required and operational simplicity matters.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Independent order processors

Constraint: billing, fulfillment, and analytics must each process every order independently and survive downtime. Design: publish to SNS with a separate SQS subscription per consumer. Why alternatives fail: one shared queue load-balances messages instead of copying them, and direct calls couple availability.

1 SNS copies each event →2 SQS buffers per consumer →3 Policies isolate access
WORKED SCENARIO

Long-running approval flow

Constraint: a process waits for approval, branches on risk, and retries selected steps for days. Design: Step Functions Standard orchestrates services with waits, choices, and error handling. Why alternatives fail: Lambda cannot run for days, and SQS alone does not model workflow state.

1 Standard supports long runs →2 State machine records progress →3 Retries are per state
WORKED SCENARIO

Cross-application business events

Constraint: many targets need only events matching attributes such as source and detail type. Design: EventBridge rules filter events and route them to targets, with archives or DLQs where needed. Why alternatives fail: SNS filtering is subscription-oriented, and SQS is not an event bus.

1 Rules match content →2 Bus decouples producers →3 Targets receive selected events

06 · KNOWLEDGE CHECK

Five SAA-style questions

Q1Three services must each receive every order event and process at different rates without losing messages during outages. Which architecture is best?
Answer: B. SNS provides fan-out, while a separate SQS queue gives every service an independent durable backlog.
Q2A payment processor requires ordered messages per customer while different customers can run in parallel. Which SQS feature provides this behavior?
Answer: B. FIFO message groups preserve order within each group while allowing multiple groups to be processed concurrently.
Q3A workflow can run for several hours and needs an auditable execution history, human waits, and exactly-once workflow execution semantics. Which service fits?
Answer: A. Standard Workflows support long-running, auditable executions and exactly-once workflow execution semantics.
Q4An SQS consumer repeatedly fails a poison message and blocks useful retries. What configuration isolates it after a bounded receive count?
Answer: A. The redrive policy moves a message to the DLQ after its receive count exceeds maxReceiveCount.
Q5A SaaS application emits events that must route to targets according to fields in each JSON event, with minimal custom routing code. Choose the service.
Answer: A. EventBridge event patterns filter structured events and rules route matching events to supported targets.
