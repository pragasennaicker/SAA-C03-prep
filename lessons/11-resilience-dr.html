Replication / backup

Pilot light

A second Region with data replicating and compute small. You scale out at failover. Warm standby keeps more compute running.

ARCHITECTURE

The primary Region serves traffic. Data replicates. Pilot light stays small until Route 53 failover, then compute scales out.

02 · DEEP DIVE

What you actually need to understand

1

HA vs fault tolerance vs DR

  • High availability minimizes downtime through redundant resources and automated failover.
  • Fault-tolerant designs continue operating despite component failures with minimal interruption.
  • Disaster recovery restores or shifts a workload after major failures such as a regional event.
  • A Multi-AZ design protects against AZ failure but is not automatically a complete regional DR strategy.
2

RPO + RTO

  • RPO is the maximum acceptable period of data loss measured backward from an incident.
  • RTO is the maximum acceptable time to restore service.
  • Lower RPO/RTO usually requires more replication, pre-provisioned capacity and automation.
  • The exam often gives RPO/RTO clues indirectly: 'no more than 5 minutes of data loss' is RPO.
3

DR strategies

  • Backup & restore: minimal standing infrastructure; lowest cost, longer recovery.
  • Pilot light: core data/services replicated and essential infrastructure kept ready; scale remaining components during recovery.
  • Warm standby: smaller but fully functional environment continuously running.
  • Multi-site active-active: multiple production environments serve traffic; fastest recovery but highest cost/complexity.
4

Data durability

  • Use service-native Multi-AZ replication for local availability.
  • Cross-Region replication/backup protects against regional failures according to service semantics.
  • Cross-account backups can reduce blast radius for destructive credentials/account compromise.
  • Test restore/failover procedures; untested backup plans are not reliable recovery plans.
5

Failure automation

  • Route 53 health/failover can switch DNS endpoints.
  • Auto Scaling replaces unhealthy compute; load balancers route around unhealthy targets.
  • Infrastructure as code accelerates reproducible recovery.
  • Service quotas in standby Regions must be sufficient before a disaster.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Recover a noncritical application

A system can lose up to 24 hours of data and remain offline for a day, while minimizing steady-state cost. Use cross-Region backups with infrastructure as code and a tested restore runbook. Warm standby pays for running capacity that the RTO does not require, and multi-site is far more expensive.

1 Long RPO→2 Long RTO→3 Lowest standby cost
WORKED SCENARIO

Keep a scaled-down recovery stack

A business service needs a minutes-level RTO and very low RPO in a second Region, but cannot fund full duplicate capacity. Run a warm standby with replicated data and reduced application capacity, then scale on failover. Pilot light may need too much provisioning time, while multi-site pays for full active capacity.

1 Stack already live→2 Scale on failover→3 Replicated data
WORKED SCENARIO

Serve from both Regions

A revenue platform requires near-zero RTO and RPO and can accept the highest operating cost and application complexity. Use multi-site active-active architecture with globally replicated data and health-based traffic steering. Backups, pilot light, and warm standby all require startup or scaling that violates the recovery objective.

1 Both sites active→2 Immediate routing→3 Highest readiness
05 · EXAM LANGUAGE DECODER

Words in the question that should trigger a design instinct

“data loss of at most X minutes”
→ RPO.
“service restored within X minutes”
→ RTO.
“scaled-down working secondary”
→ Warm standby.
“only core components running”
→ Pilot light.
“both Regions serve users”
→ Active-active.
“protect from AZ failure”
→ Multi-AZ.
06 · KNOWLEDGE CHECK

Twenty-five SAA-style questions

Q1A retail company runs an order API on Amazon EC2 behind an Application Load Balancer in a single AWS Region. The database is Amazon RDS with Multi-AZ enabled, and an Availability Zone outage last year caused no customer impact. Compliance now requires the workload to recover if the entire Region fails, with at most one hour of data loss. Which solution will meet these requirements?
Answer: A. The new failure domain is a whole Region. Multi-AZ high availability stays inside one Region, so recovery needs a second-Region copy and a failover plan.

Good to know: More AZs, a larger RDS class, or a different load-balancer type would still be in-Region high availability. They would be right if the stem only required surviving an Availability Zone failure.
Q2A payments team says that after a regional disaster the application may lose at most 5 minutes of committed transactions. Operators may take several hours to restore compute. The company wants the MOST cost-effective design that still meets that data-loss limit and will not run a second production fleet. Which solution will meet these requirements?
Answer: C. Five minutes of acceptable data loss is the recovery point objective. Frequent cross-Region copies satisfy RPO while hours of restore time allow backup/restore compute instead of a standing second fleet.

Good to know: Warm standby or active-active would be correct if the stem also demanded minutes-level restore time or near-zero downtime. Weekly same-Region snapshots miss both the RPO and the regional failure domain.
Q3A hospital portal can lose up to 24 hours of nonclinical analytics data. After a regional outage the portal must be usable again within 15 minutes. Finance will not pay for two full-capacity production Regions. A smaller copy of the application must already pass health checks, then scale out. Which solution will meet these requirements?
Answer: B. A 15-minute restore time needs a stack that is already running, which is warm standby. A 24-hour data-loss window does not justify paying for a second full production site.

Good to know: Backup and restore would fit if RTO were measured in hours or a day. Active-active would fit if both sites had to serve users already and cost were secondary. In-Region Multi-AZ does not recover a failed Region.
Q4A monthly reporting job runs on Amazon EC2 and writes results to Amazon EBS. The company can lose up to 24 hours of reports and can wait a day to restore the job after a Region failure. Leadership wants the LOWEST ongoing disaster recovery cost and will not keep spare instances running. Which solution will meet these requirements?
Answer: D. Long recovery point and restore times plus minimum standby cost select backup and restore. Warm standby and active-active pay for running capacity the RTO does not require.

Good to know: Warm standby would be the answer if the job had to resume in minutes. Multi-AZ placement is high availability in one Region, not a regional recovery site.
Q5A SaaS vendor must recover from a Region failure with a low recovery point objective. It will pay for replicated data and a small core of always-on services in a second Region, but it will not run a full application stack there until failover. Application instances will launch from templates after the disaster is declared. Which solution will meet these requirements?
Answer: A. Core data and essential services kept ready, with the rest of compute launched at disaster time, is pilot light. That is warmer than backup-only and cooler than a working scaled-down fleet.

Good to know: Warm standby would be correct if a smaller full application stack already had to pass health checks. Weekly backups would miss a low RPO. Active-active would be correct if both sites already served users.
Q6A business service needs a minutes-level recovery time and a very low recovery point in a second AWS Region. The company cannot fund a duplicate full-capacity production fleet. A smaller copy of the application must already be running and able to pass health checks, then grow after failover. Which solution will meet these requirements?
Answer: C. A smaller but fully functional environment that is already running is warm standby. Pilot light keeps only the core, so provisioning the rest can miss a minutes-level RTO.

Good to know: Pilot light would be correct if only core data services had to run until failover and a longer scale-out were acceptable. Active-active would be correct if both Regions already had to serve production traffic.
Q7A payments company runs a revenue platform on Amazon EC2 and Amazon RDS in one AWS Region. The platform requires near-zero recovery time and data loss if that Region fails. Both sites must already serve production users. The company accepts the highest operating cost. Backups and standby scale-out would violate those objectives. Which solution will meet these requirements?
Answer: B. Near-zero RTO and RPO with both sites already serving users is active-active. Backup, pilot light, and warm standby all require startup or scaling that breaks that objective.

Good to know: Warm standby would be correct if a minutes-level RTO and a scaled-down idle stack were enough. Pilot light and backup/restore fit longer RTOs at lower cost.
Q8A company uses AWS Backup for Amazon EBS volumes and Amazon EFS file systems in the US East (N. Virginia) Region. A regional disaster requirement says recovery must still be possible if that Region is unavailable. The recovery point may be measured in hours. Which solution will meet these requirements?
Answer: D. A Region failure makes in-Region snapshots unreachable. Cross-Region copies of AWS Backup recovery points provide a restore source in another Region.

Good to know: More frequent same-Region snapshots would tighten RPO only while that Region still works. Multi-Attach and instance store do not create a second-Region recovery copy.
Q9Compliance requires that backups of production Amazon EBS volumes and Amazon RDS databases remain restorable if the workload AWS account is compromised and resources are deleted. Copies must not exist only in that account. The company already uses AWS Backup in the production account. Which solution will meet these requirements?
Answer: A. Cross-account backup copies reduce blast radius when credentials in the workload account can delete local snapshots. Same-account Multi-AZ or extra AZs still sit inside the compromised account.

Good to know: Cross-Region copies in the same account help a regional outage but not an account wipe. Pair cross-account with cross-Region when the stem demands both failure domains.
Q10A company copies Amazon EBS snapshots of its application volumes to a second Region every night. Auditors found that nobody has ever launched an instance from those snapshots. The disaster recovery plan must prove that restores work before the next audit, not only that snapshot jobs completed. Which solution will meet these requirements?
Answer: C. Untested backups are not a recovery plan. A scheduled restore that boots the application is the proof auditors asked for.

Good to know: Longer retention helps how long you can go back, not whether a restore works. Tags and in-Region Auto Scaling do not exercise the standby Region.
Q11An application has a primary Application Load Balancer in us-east-1 and a recovery load balancer in us-west-2. When the primary Region is unhealthy, DNS must answer with the recovery endpoint only. Weighted experiments, latency-based Region choice, and splitting traffic in normal operation are not the goal. Which solution will meet these requirements?
Answer: B. Active/passive DNS with a health check is Route 53 failover. Weighted and latency policies steer for split or nearest Region, not primary-then-secondary.

Good to know: Weighted routing would be correct for a 90/10 release. Latency routing would be correct if users should land in the lowest-latency healthy Region. Auto Scaling groups do not span Regions.
Q12A web fleet runs on Amazon EC2 in three Availability Zones behind an Application Load Balancer in one AWS Region. Instances sometimes fail target-group health checks. The company needs replacement capacity automatically in the same Region and does not have a second-Region disaster requirement. Which solution will meet these requirements?
Answer: D. Instance-level failure in one Region is Auto Scaling replacement plus a load balancer that routes around unhealthy targets. That is high availability automation, not regional disaster recovery.

Good to know: Route 53 failover and cross-Region AMIs would appear if the stem required a second Region. A single instance store host is the opposite of automated replacement.
Q13A company uses backup and restore for a noncritical application on Amazon EC2. After a Region failure, operators previously rebuilt subnets, security groups, and Auto Scaling groups by clicking in the console, which missed the recovery time objective. Data backups already exist in the second Region. Which solution will meet these requirements?
Answer: A. Backup/restore RTO depends on how fast the empty Region can be rebuilt. Infrastructure as code makes that rebuild repeatable instead of console drift.

Good to know: Active-active would be correct if near-zero RTO required standing production in both Regions. Growing Multi-AZ in a Region that is already down does not help recovery.
Q14A company maintains a warm standby web fleet in the Europe (Ireland) Region. During a game-day test, Auto Scaling could not launch enough Amazon EC2 instances because the account was already at the On-Demand instance quota there. Production failover would have missed the recovery time objective. Which solution will meet these requirements?
Answer: C. Service quotas are per Region. A standby that cannot scale to production size fails RTO even if the architecture pattern is correct.

Good to know: Placement groups and disabling Auto Scaling do not raise the standby Region limit. Quotas must be requested and tested before a real disaster.
Q15A payments API on Amazon EC2 must keep processing authorizations if a single instance or a single Availability Zone fails, with no operator restore from backup. A full AWS Region failure is out of scope, and the company will not build a second Region for this workload. Which solution will meet these requirements?
Answer: B. Surviving instance and AZ failure without a restore is in-Region high availability: redundant AZs, a load balancer, and Auto Scaling. Regional DR patterns are the wrong failure domain here.

Good to know: Pilot light, cross-Region backups, and DNS failover to an error page would appear if the stem required a regional disaster plan. They do not keep the API processing during an AZ outage.
Q16An Amazon RDS database already uses Multi-AZ and survived an Availability Zone outage with automatic failover. A new requirement is to recover if the entire Region becomes unavailable, with hours of acceptable restore time. The team wants a managed copy rather than a second writer in production. Which solution will meet these requirements?
Answer: D. Multi-AZ is high availability inside one Region. A Region-level disaster needs a copy outside that Region, which backups or a cross-Region replica provide.

Good to know: Extra in-Region Multi-AZ capacity would still fail with the Region. A cross-Region read replica promoted at failover is the warmer form of the same regional-DR idea.
Q17A compliance application on Amazon RDS may lose at most 15 minutes of data if a Region fails, but the application tier on Amazon EC2 may take 4 hours to rebuild. The company will not run application servers in the second Region until a disaster is declared. Which solution will meet these requirements?
Answer: A. Recovery point and recovery time are independent. Tight RPO drives frequent cross-Region data copies; a 4-hour RTO allows compute to be rebuilt instead of kept warm.

Good to know: Warm application capacity would be correct if the 4-hour rebuild missed RTO. Weekly database backups would miss the 15-minute RPO. Multi-AZ alone is not regional DR.
Q18A company currently takes nightly AWS Backup jobs of Amazon EBS volumes to a second Region. A new product owner says the workload may lose at most 15 minutes of data. Restore time may still be several hours, and the company does not want a second live application fleet. Which solution will meet these requirements?
Answer: C. Nightly copies imply up to a day of data loss. A 15-minute RPO requires more frequent backups or replication; hours of RTO still allow backup/restore compute.

Good to know: Active-active would be correct if restore time also had to be near zero. Placement groups and dropping backups do not tighten the recovery point.
Q19A noncritical batch application on Amazon EC2 can lose 24 hours of data and can be down for a day after a Region failure. The company wants the LOWEST standby cost and a tested path to rebuild the stack in another Region. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and C. Long RPO and RTO select backup/restore: cross-Region recovery points plus a repeatable rebuild. Standing warm or active-active capacity is extra cost.

Good to know: Warm standby would be jointly correct if the stem required a minutes-level RTO. Turning backups off would remove the only recovery copy.
Q20Core databases must already exist in a second AWS Region so data loss stays in minutes. Application Auto Scaling groups should be created only after failover is declared. The company will not pay for a fully functional scaled-down web tier that runs all month. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and D. Pilot light keeps core data ready and scales the rest of compute at disaster time. Those two steps are jointly necessary for this cost and RPO mix.

Good to know: Continuous user traffic from the second Region is active-active. Weekly backups alone would miss a minutes-level RPO. A single AZ weakens the primary site without building a pilot light.
Q21A customer-support portal on Amazon EC2 needs a minutes-level recovery time in a second Region and a very low recovery point. Finance will not fund a second full-capacity site. A smaller stack must already be healthy, then grow after DNS failover. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: C and E. Warm standby is a smaller live stack plus a health-aware cutover and scale-out. AMI copies with no running stack are backup/restore, which is too cold for minutes-level RTO.

Good to know: Multi-AZ in the primary Region still fails with that Region. Running only in the standby Region is a migration, not a dual-site recovery design.
Q22A trading portal on Amazon EC2 and Amazon RDS requires near-zero recovery time and data loss if one AWS Region fails. Both sites must already serve production users, and the company accepts the highest cost. Scale-out after a disaster would be too slow. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and E. Active-active needs live capacity and data in two Regions plus health-aware DNS so clients already use both sites and drop an unhealthy one.

Good to know: Zero compute until a ticket is pilot light or backup/restore. Daily single-Region snapshots miss both RPO and the regional failure domain.
Q23Production Amazon EBS volumes and Amazon RDS instances must remain restorable after two events: the workload AWS account is compromised, and the primary Region is unavailable. A single AWS Backup plan already covers those resource types in the production account. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and C. Region failure needs a copy outside the primary Region. Account compromise needs a copy outside the workload account. AWS Backup can do both copies.

Good to know: RDS Multi-AZ is in-Region high availability, not an isolated backup vault. A public bucket would expose backup data rather than shrink blast radius.
Q24A company has a documented warm-standby design for an Amazon EC2 web app in a second Region. Game days have never restored a backup or scaled the standby to production size. The next audit requires proof that failover would meet the recovery time objective. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: D and E. A recovery plan is reliable only if restores are tested and the standby Region can actually launch the scaled-out size. Completed backup jobs do not prove either.

Good to know: Quota cuts in the primary Region are not a test strategy. Instance store is ephemeral and is not a backup target.
Q25A web API must fail over from a primary Application Load Balancer in one Region to a recovery load balancer in a second Region when the primary endpoint is unhealthy. Operators must not split traffic 50/50 in normal operation. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and B. Active/passive DNS is failover records plus a health check on the primary. Weighted 50/50 is a split, not a standby. Geolocation steers by user location.

Good to know: Weighted routing with health checks would be correct for a canary or active-active share. Same-AZ endpoints would not be a regional recovery pair.
