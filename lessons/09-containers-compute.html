VPC

ECS on Fargate

ECS is the orchestrator. Fargate removes the EC2 node layer. Least ops for request/response containers.

ARCHITECTURE

ALB

Path-based routing to ECS services. Target type is IP for Fargate.

ARCHITECTURE

EKS

When you need Kubernetes APIs. AWS runs the control plane; you still choose nodes or Fargate.

ARCHITECTURE

AWS Batch

Queued jobs, not a request/response API. It can use Fargate or EC2 underneath.

ARCHITECTURE

The full container path

Users hit the ALB; Fargate tasks in private subnets pull images from ECR. EKS is the Kubernetes alternative; Batch is for jobs.

02 · DEEP DIVE

What you actually need to understand

1

ECS

  • AWS-native container orchestration with services/tasks and tight AWS integration.
  • Can run tasks on EC2 capacity or Fargate.
  • ECS services maintain desired task count and integrate with load balancers/autoscaling.
  • Good default when Kubernetes APIs/ecosystem are not a requirement.
2

EKS

  • Managed Kubernetes control plane and AWS integrations.
  • Use when Kubernetes portability/ecosystem/API compatibility is a real requirement.
  • Worker compute can be EC2 managed node groups or Fargate for supported workloads.
  • Kubernetes adds operational concepts; do not choose it merely because it is fashionable.
3

Fargate

  • Serverless compute engine for containers used with ECS and EKS.
  • Removes EC2 worker-node provisioning/patching responsibilities.
  • Pay for task/pod compute resources rather than idle cluster instances.
  • Useful when container packaging is desired but infrastructure management should be minimized.
4

ECR + image lifecycle

  • Private/public container registry integrated with IAM.
  • Store versioned images and scan/manage lifecycle according to requirements.
  • Orchestrators pull images from ECR and run them; ECR itself does not execute containers.
  • Immutable image/versioning practices improve repeatability.
5

Batch + platform options

  • AWS Batch schedules queued batch jobs onto suitable compute resources.
  • Elastic Beanstalk abstracts much of application environment provisioning while retaining underlying AWS resources.
  • Outposts extends AWS infrastructure on premises for latency/data-residency use cases.
  • ECS/EKS Anywhere are recognition-level options for customer-managed/on-premises container environments.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Simple microservice platform

Constraint: a small team needs managed container orchestration without Kubernetes expertise. Design: ECS services on Fargate pull private images from ECR and register tasks with an ALB. Why alternatives fail: EKS adds Kubernetes administration, while plain EC2 lacks orchestration.

1 ECS minimizes control work→2 Fargate removes nodes→3 ECR stores images
WORKED SCENARIO

Portable Kubernetes workloads

Constraint: an organization requires Kubernetes APIs, Helm charts, and familiar ecosystem tooling. Design: EKS supplies the managed control plane with managed node groups or Fargate profiles. Why alternatives fail: ECS does not expose Kubernetes APIs, and self-managed Kubernetes increases operational burden.

1 EKS preserves Kubernetes→2 Nodes or Fargate run pods→3 AWS manages control plane
WORKED SCENARIO

Private image delivery

Constraint: deployments need private, scanned, versioned images close to AWS compute. Design: push immutable tags to ECR, enable scanning, and grant task execution roles pull access. Why alternatives fail: S3 is not an OCI registry, and public registries weaken private access control.

1 ECR is managed registry→2 Execution role pulls→3 Immutable tags reduce drift

06 · KNOWLEDGE CHECK

Twenty-five SAA-style questions

Q1A startup hosts a request/response HTTP API as containers in one AWS Region. A two-person team has no Kubernetes experience and must not patch worker nodes or pay for idle cluster instances between traffic spikes. Images must remain private. Tasks must run in private subnets, and users must reach the API through a public Application Load Balancer. Which solution will meet these requirements?
Answer: A. No Kubernetes API requirement plus no worker-node management selects ECS on Fargate. ECR holds private images; ECS keeps the desired task count behind the ALB.

Good to know: EKS would be correct if Helm, operators, or the Kubernetes API were required. Plain EC2 has no service scheduler to replace unhealthy copies.
Q2A company already operates Helm charts and Kubernetes operators in another cloud. After moving to AWS it must keep those APIs and the same ecosystem tooling. AWS should run the Kubernetes control plane. The team will choose worker compute separately and does not want to operate etcd itself. Existing charts must deploy without a rewrite to Amazon ECS task definitions. Which solution will meet these requirements?
Answer: C. Helm, operators, and Kubernetes API compatibility select EKS. AWS manages the control plane; ECS does not expose those APIs.

Good to know: ECS on Fargate would be the lower-operations answer if Kubernetes were not required. Batch schedules finite jobs, not a long-running Kubernetes platform.
Q3An Amazon ECS service already runs a containerized HTTP API on Amazon EC2 container instances. Operators spend too much time patching those instances and still pay for idle cluster capacity between spikes. The team must keep ECS as the orchestrator and must stop managing worker AMIs and capacity providers. Which solution will meet these requirements?
Answer: B. Fargate is the serverless compute engine for ECS tasks, so operators no longer provision or patch worker nodes and they pay for task resources rather than idle instances.

Good to know: ECS on EC2 would remain correct if the stem required custom AMIs or instance types that the team must manage. Dedicated Hosts increase host control, not reduce it.
Q4A platform team must store versioned, private container images next to AWS compute in the same Region. Orchestrators will pull those images at deploy time. The store must integrate with IAM and must not be the runtime that executes containers. A public registry is not acceptable for these images. Which solution will meet these requirements?
Answer: D. ECR is the managed registry. Orchestrators pull and run images; ECR itself does not execute containers. S3 is object storage, not an OCI registry.

Good to know: A public registry would fit only if images were allowed to be world-readable. Lifecycle rules expire old tags; they are not a task runtime.
Q5A genomics lab submits thousands of finite analysis jobs that wait until compute is free. The jobs are not a long-running HTTP service. Researchers may outpace capacity, so work must queue. The lab wants AWS to schedule jobs onto Fargate or Amazon EC2 and does not need Kubernetes APIs. Which solution will meet these requirements?
Answer: A. Queued finite jobs select AWS Batch, which schedules onto Fargate or EC2. An always-on ECS service is for long-running request/response capacity, not a job queue.

Good to know: ECS would be correct for a steady HTTP API with a desired task count. EKS would appear if Kubernetes Job APIs were the constraint.
Q6A product team needs to deploy a conventional web application with the LEAST operational overhead for environment provisioning. The application is not containerized and does not need Kubernetes. The team still wants AWS to create the underlying load balancer and compute rather than assembling every resource by hand. Which solution will meet these requirements?
Answer: C. Elastic Beanstalk abstracts application environment provisioning while still using underlying AWS resources. EKS and Batch do not match an uncontainerized web environment.

Good to know: ECS on Fargate would be the answer after the app is packaged as containers and Kubernetes is still not required. Outposts is for on-premises latency or residency, not simpler Region provisioning.
Q7A factory must run an AWS-based control application beside the production line. Round-trip latency to the nearest AWS Region is too high for the control loop, and some process data must remain on the factory floor. The company wants AWS-designed infrastructure on premises rather than a fully custom private cloud. Which solution will meet these requirements?
Answer: B. Outposts extends AWS infrastructure on premises for latency and data-residency constraints. More Regional Fargate or Beanstalk capacity does not move the control loop onto the factory floor.

Good to know: ECS Anywhere would be the recognition-level answer if the stem required the ECS task model on customer-owned servers rather than AWS-owned Outposts hardware.
Q8A retailer already owns on-premises servers in each store and wants to run Amazon ECS tasks on that hardware. Kubernetes is not required. The company will not install AWS Outposts racks. It needs AWS container tooling on customer-managed infrastructure rather than a new Regional-only cluster or a Batch queue in the closest Region. Which solution will meet these requirements?
Answer: D. ECS Anywhere is the recognition-level option for ECS on customer-managed or on-premises hosts. Outposts is AWS infrastructure placed on site, which this stem rejects.

Good to know: EKS Anywhere would appear if the constraint were Kubernetes on customer-managed hardware. Batch in the Region cannot meet store-floor latency on existing boxes.
Q9A checkout path must run a short function whenever an order event arrives. Each invocation finishes in seconds, needs no container orchestrator, and should incur no idle instance cost. The team does not need Kubernetes APIs and is not packaging a long-running HTTP service. AWS Batch on an hourly schedule is too slow for checkout. Which solution will meet these requirements?
Answer: A. Short event-driven functions select Lambda. EKS nodes and hourly Batch jobs add idle capacity or delay that the stem does not ask for.

Good to know: ECS on Fargate would be correct for a long-running containerized API. Lesson 08 owns Lambda concurrency and API Gateway details; this item only picks the function compute model.
Q10A vendor ships a network appliance as an Amazon Machine Image that needs custom kernel modules, a specific Linux distribution, and full operating-system access. The workload is not packaged as a container and is not a short function. The company will run it in AWS and must retain maximum OS control. Which solution will meet these requirements?
Answer: C. Maximum OS control, custom kernels, and an AMI select EC2. Fargate and ECS hide or replace the guest OS the appliance requires. ECR does not run images.

Good to know: ECS on EC2 would be in play if the appliance were containerized but still needed managed instances. Lambda is the short-function model, which this stem excludes.
Q11A media company wants AWS-native container orchestration for a long-running video transcoder in one Region. Operators must use a custom AMI, apply their own host patches, and binpack tasks onto Reserved Instances they already purchased. Kubernetes APIs are not required. Hiding the instance layer is not acceptable. Which solution will meet these requirements?
Answer: B. ECS can run tasks on EC2 when the team must manage AMIs, patches, and instance purchases. Fargate removes that instance layer, which the stem forbids.

Good to know: Fargate is the answer when the constraint is no worker-node management. EKS is for Kubernetes portability, not a default for every container.
Q12An enterprise is moving a platform that already uses Kubernetes APIs and Helm charts. After the move to AWS it must keep that tooling. It also refuses to provision or patch worker nodes. Supported pods can run on serverless container compute. AWS must still operate the Kubernetes control plane. Which solution will meet these requirements?
Answer: D. Kubernetes APIs select EKS; no worker-node management selects Fargate for supported pods. ECS does not provide the Kubernetes API.

Good to know: EKS managed node groups would be correct if the stem required EC2 worker capacity the team is willing to patch. ECS on Fargate would win without Helm.
Q13A payments API is packaged as containers in one AWS Region. The service must keep six healthy copies in private subnets, replace failed copies automatically, and receive HTTPS traffic from a public Application Load Balancer. Kubernetes is not required, and the team does not want to manage worker nodes. Which solution will meet these requirements?
Answer: A. An ECS service maintains desired task count and integrates with a load balancer. Fargate removes node work. ECR is a registry, not a listener.

Good to know: Host and path listener rules are a Lesson 03 ALB topic; this item only tests ECS desired count plus ALB integration. Batch is for queued jobs, not six always-on API copies.
Q14A hospital runs Amazon ECS tasks in private subnets in one Region. It must keep container images private, scan them for vulnerabilities, and tag them immutably so deploys are repeatable. Tasks will pull images at launch using IAM rather than a shared password. Developers must not embed registry credentials in task definitions. Which solution will meet these requirements?
Answer: C. ECR provides private, scannable, versioned images. The task execution role pulls at launch without embedding secrets in the definition.

Good to know: S3 is not an OCI registry. A public registry would violate the private-image constraint even if scanning existed elsewhere.
Q15A two-person team is launching a containerized internal API on AWS in a single account. They have no Helm charts, no operators, and no requirement for the Kubernetes API. They want AWS-native orchestration and will not add Kubernetes operational concepts for fashion. Worker-node patching should be avoided. Which solution will meet these requirements?
Answer: B. When Kubernetes APIs are not required, ECS is the AWS-native orchestrator. Fargate removes node patching. EKS is not the default merely because workloads are containers.

Good to know: EKS is correct when Helm, operators, or portability of the Kubernetes API are real constraints. Batch remains the queued-job answer.
Q16A company currently runs Kubernetes itself on Amazon EC2, including etcd and control-plane nodes. It must keep Helm and the Kubernetes API but wants AWS to operate the control plane. Worker nodes can remain EC2 managed node groups. The team will not switch to Amazon ECS. Which solution will meet these requirements?
Answer: D. EKS is the managed Kubernetes control plane. Managed node groups keep EC2 workers without self-managed etcd. ECS would abandon the Kubernetes API the stem requires.

Good to know: EKS on Fargate would fit if the stem also forbade worker-node management. Self-managed Kubernetes on EC2 is what the company is leaving.
Q17A video processor runs for 45 minutes per file, needs a custom runtime inside a container, and must scale copies from a queue of work. The team does not want to manage Kubernetes. A short function model is too brief for each file, and Amazon ECR must not be treated as the compute engine. Which solution will meet these requirements?
Answer: A. Long-running container work without Kubernetes selects ECS. Fargate avoids node management. Lambda is the short-function model; ECR does not execute containers.

Good to know: AWS Batch would be equally reasonable if the stem stressed a managed job scheduler rather than an ECS task worker. Lambda remains Lesson 08's short-event path.
Q18A university runs nightly simulation jobs that each last two hours and then stop. Between runs, no compute should sit idle. Jobs must queue when researchers submit more work than capacity. The team will not operate a Kubernetes control plane and does not need a 24-hour HTTP service. Which solution will meet these requirements?
Answer: C. Finite queued jobs that should not leave idle service capacity select Batch. A high desired count on ECS or EKS keeps compute running between nights.

Good to know: An ECS service is the right shape for a continuously listening API. Fargate under Batch still pays for job compute rather than an always-on service.
Q19A catalog API is packaged as containers. The team has no Helm charts and no Kubernetes requirement. It must not patch worker nodes. Private images will live in a registry, and a public Application Load Balancer will send HTTPS to the service in private subnets. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and C. ECS is the AWS-native orchestrator; Fargate removes the node layer. Both are required for this constraint set. ECR stores images but does not run them.

Good to know: EKS plus Fargate would be the pair if Kubernetes APIs were mandatory. Batch would pair with a job queue, not a public HTTP API.
Q20An organization is moving platform tooling that depends on Helm charts, custom operators, and the Kubernetes API. AWS must run the control plane. The team will keep those manifests rather than rewriting them as Amazon ECS task definitions. Worker compute can be chosen after the cluster exists. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and D. EKS supplies the managed Kubernetes API; deploying Helm and operators is how the existing ecosystem keeps working. Those two steps are jointly necessary.

Good to know: Add Fargate profiles if the stem also forbids worker-node patching. ECS cannot run Helm operators.
Q21Amazon ECS tasks in private subnets must start from private, scanned, immutable image tags. The registry must integrate with IAM. Tasks must pull at launch without a password in the task definition, and the registry must not be treated as compute. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: C and E. ECR holds the private versioned images; the execution role is how ECS pulls them. Public access and treating ECR as compute both violate the stem.

Good to know: Image scanning on the repository is the usual next control when the stem also names vulnerability findings. S3 Glacier is archive object storage, not a registry.
Q22A research group submits finite rendering jobs that must wait in a queue until capacity exists. Jobs should run on Fargate or Amazon EC2 according to cost. The group will not keep a 24-hour Amazon ECS service at peak desired count and does not need Kubernetes. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and E. Batch is the scheduler for queued jobs; a compute environment is where those jobs actually run. An always-on ECS desired count fights the idle-capacity constraint.

Good to know: ECS services remain the answer for long-running APIs with a load balancer. EKS Jobs would appear only if Kubernetes were required.
Q23A plant-floor controller must run on AWS-designed hardware next to the line because Regional round-trip time is too high and process data must stay on site. The company does not want to rewrite the controller as a short function in the Region. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and C. Outposts places AWS infrastructure on premises; the workload must actually run there to meet latency and residency. Regional Fargate still leaves the plant.

Good to know: ECS Anywhere would be the pair if the stem required ECS on servers the plant already owns. CloudFront is an edge cache, not a residency control plane.
Q24A public HTTPS API will run as containers in private subnets in one Region. The platform must keep a stated number of healthy copies, replace failed copies, and register those copies with an Application Load Balancer that already sits in public subnets. Kubernetes is not required. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: D and E. ECS services maintain desired count and integrate with load balancers. Those two controls match the stem. ECR and Batch are not HTTPS listeners.

Good to know: ALB host and path rules belong to Lesson 03. Fargate would be the launch-type add-on if the stem also forbade worker-node patching.
Q25A product team wants to deploy a conventional, uncontainerized web application in one AWS Region and let AWS provision the environment, including underlying load balancing and compute. They do not need Kubernetes, AWS Batch, or on-premises racks, and they will not assemble every resource by hand. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and B. Beanstalk is the environment-provisioning abstraction; uploading the bundle is how the app gets onto the resources Beanstalk creates.

Good to know: ECS on Fargate would be the pair after the app is containerized and Kubernetes is still not required. Outposts is latency or residency, not simpler PaaS.
