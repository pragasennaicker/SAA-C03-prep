01 · ARCHITECTURE DRAWING

Build organization, federation, and workload roles

ARCHITECTURE

Organizations

The management account owns the org. Member accounts sit in OUs. This is the skeleton every later identity control hangs on.

ARCHITECTURE

Service Control Policy

SCPs are guardrails from the management account. They limit every identity policy beneath them, including the account root.

ARCHITECTURE

IAM Identity Center

Workforce federates here — not long-lived IAM users in every account. Permission sets map to IAM roles in members.

ARCHITECTURE

IAM Role

Workloads assume roles. EC2 uses an instance profile. Prefer roles over access keys.

ARCHITECTURE

STS

Security Token Service issues the temporary credentials when a role is assumed.

ARCHITECTURE

Permission boundary

A maximum ceiling on what a delegated admin can grant. It does not grant access by itself.

ARCHITECTURE

The full identity path

SCPs cap the org. People federate with Identity Center. Workloads assume roles via STS, optionally capped by a permission boundary.

02 · DEEP DIVE

What you actually need to understand

1

Principals + temporary credentials

  • IAM users are long-lived identities and should be minimized for human access.
  • IAM roles are assumed and provide temporary credentials through AWS STS.
  • EC2, Lambda and other AWS workloads should use service roles instead of hard-coded access keys.
  • Cross-account access commonly uses a trust policy on a role plus permissions granted to the role.
2

Policy evaluation

  • Start by asking whether an applicable explicit deny exists; explicit deny wins.
  • An allow must exist in the effective policy set unless access is granted through an applicable resource-based mechanism.
  • Identity policies say what a principal may do; resource policies say who may access a resource.
  • Permissions boundaries limit the maximum identity-based permissions a user/role can receive.
3

Organizations + SCPs

  • AWS Organizations groups accounts into organizational units.
  • SCPs set maximum permissions for member accounts/OUs; they do not grant permissions.
  • Use multiple accounts to reduce blast radius and separate production, security/logging and workloads.
  • Resource Access Manager can share supported resources across accounts without duplicating them.
4

IAM Identity Center

  • Centralizes workforce sign-in to many AWS accounts and applications.
  • Permission sets map workforce groups/users to account permissions.
  • External identity providers can federate users, avoiding IAM users in each account.
  • Distinguish workforce identity from customer identity (Cognito).
5

Root + least privilege

  • Protect the root user with strong controls and avoid routine use.
  • Use MFA for privileged human access.
  • Continuously reduce broad permissions based on actual need.
  • Prefer short-lived credentials and role assumption over long-lived access keys.

04 · WORKED SCENARIOS

Apply the concepts as an architect

WORKED SCENARIO

Read data with a role

An application in Account A needs limited access to a bucket in Account B without shared credentials. Create a role in B with bucket permissions and trust A to assume it through STS, adding external ID conditions for a third party. Copying access keys creates long-lived secret risk, while an SCP cannot grant bucket access.

1 Temporary credentials→2 Scoped trust→3 No key sharing
WORKED SCENARIO

Restrict member-account Regions

Security must prevent member accounts from creating most resources outside approved Regions, even for account administrators. Attach an SCP with the required deny conditions to the relevant OU, exempting global services carefully. IAM policies in each account are easier to alter, and an SCP alone does not grant permitted actions.

1 OU-wide guardrail→2 Admin constrained→3 Explicit deny
WORKED SCENARIO

Delegate role creation safely

Developers may create roles but must never grant permissions beyond a security-approved ceiling. Require a permissions boundary on created roles and restrict iam:PassRole to approved roles. A normal allow policy can be changed into broader access, while an SCP is too coarse for per-role delegated limits.

1 Maximum ceiling→2 Delegated creation→3 PassRole scoped

06 · KNOWLEDGE CHECK

Twenty-five SAA-style questions

Q1An application on Amazon EC2 in private subnets must read objects from Amazon S3. Security forbids long-lived access keys on the instance, in user data, or in the AMI. The company will not use the root user. Temporary credentials must be issued to the workload automatically. Which solution will meet these requirements?
Answer: A. EC2 workloads use a service role (instance profile) so STS can issue temporary credentials. SCPs do not grant permissions to the instance.

Good to know: An IAM user key in the AMI would be the (insecure) answer only if the stem allowed long-lived secrets on disk. An SCP is a permission ceiling, not a grant.
Q2AWS Lambda functions process files and must write results to Amazon DynamoDB. The team must not store IAM user access keys in environment variables or in the function package. Credentials should be temporary and rotated by AWS. The functions already run in one account. Which solution will meet these requirements?
Answer: C. Lambda uses an execution role for temporary STS credentials. User or root access keys are long-lived secrets the stem forbids.

Good to know: An IAM user key in the environment would be the anti-pattern if the stem had allowed packaged secrets. Identity Center is for workforce SSO, not the function’s AWS API calls.
Q3A company still creates an IAM user with access keys for every employee who uses the AWS Management Console. Security wants to stop minting long-lived user credentials for people and to federate staff instead. Customer sign-in to a mobile app is a separate project and must not drive this choice. Which solution will meet these requirements?
Answer: B. Workforce SSO across accounts is IAM Identity Center. Cognito is the customer and application identity service, not the staff console path the lesson teaches.

Good to know: Cognito would be the answer if the stem were customer sign-up and sign-in for an app. IAM users remain a legacy option when federation is not yet available.
Q4Administrators in Account A must perform limited actions in Account B for one hour at a time. The companies refuse to copy IAM user access keys between accounts. Account B should issue temporary credentials after a successful assume. An SCP must not be used as the way to grant the administrators permissions. Which solution will meet these requirements?
Answer: D. Cross-account temporary access is AssumeRole through STS. SCPs do not grant permissions in the target account.

Good to know: A bucket or table resource policy would appear if the stem kept the principal in Account A without assuming a role in B. Cognito is customer identity, not this admin path.
Q5A company found that an IAM allow policy let operators delete production objects. Security wants those deletes blocked for that identity even if other allow statements remain. The block must win during policy evaluation. The team will not rely on hunting down every allow by hand. Which solution will meet these requirements?
Answer: A. An applicable explicit deny wins over allows. A second allow cannot override that deny, and an SCP allow does not grant the delete.

Good to know: A second allow would have been enough if the gap were a missing grant and no deny existed. SCPs cap member accounts; they do not grant.
Q6Security must prevent member accounts from creating most resources outside a list of approved Regions, even when those accounts’ administrators try. IAM policies in the member accounts can be edited by those administrators. The control must be an organization guardrail and must not be the mechanism that grants day-to-day permissions. Which solution will meet these requirements?
Answer: C. An SCP on the OU is the guardrail that even member administrators cannot remove. IAM policies in those accounts are easier to alter.

Good to know: An identity allow in each account would be part of granting work inside approved Regions, but it cannot stop an administrator from widening IAM. Cognito is not the org Region lock.
Q7An application role in Account A must read objects from a bucket in Account B without assuming a role in B. The role already has an identity policy that allows s3:GetObject on that bucket ARN. Access still fails. The bucket must state who may read it. The teams will not copy access keys. Which solution will meet these requirements?
Answer: B. When the principal stays in Account A, a resource policy on the bucket must allow that principal. Identity policy alone is not enough cross-account, and an SCP does not grant.

Good to know: A role in Account B that Account A assumes would be the other cross-account pattern and would not require this bucket policy shape. Identity Center is workforce SSO, not the bucket allow.
Q8Developers may create IAM roles for their applications, but security requires that no created role can ever exceed an approved permission ceiling. A normal allow policy on the developer would be too easy to widen later. An SCP on the whole OU is too coarse for this per-role cap. Which solution will meet these requirements?
Answer: D. A permissions boundary sets the maximum identity-based permissions a delegated role can receive. An SCP is an OU-wide cap, not a per-role delegation ceiling.

Good to know: An SCP would be the answer if the stem needed one guardrail on every account in an OU. Access keys would increase long-lived secret risk.
Q9A company runs production, development, and a security logging archive in one AWS account. A compromised developer key could reach production data. Leadership wants separate blast radius so that development identities cannot reach production resources by default. Central billing should remain, and the company already uses AWS Organizations. Which solution will meet these requirements?
Answer: A. Multiple Organization accounts shrink blast radius and separate production from development and logging. IAM users in one account still share that account’s blast radius.

Good to know: IAM policies and tags still matter inside an account, but they are not a substitute for account isolation when the stem demands blast-radius separation. RAM can later share selected resources across those accounts.
Q10A network account holds VPC subnets that application accounts must use for Amazon EC2. Duplicating the VPC in every account would break the central network design. The company already uses AWS Organizations and wants a managed share of supported resources rather than copied credentials. Which solution will meet these requirements?
Answer: C. AWS RAM shares supported resources such as subnets across accounts without duplicating them. An SCP cannot grant VPC ownership.

Good to know: Recreating CIDRs would be the answer only if each account needed an independent network. Access keys would share identity secrets, not the subnet resource.
Q11Employees in one corporate directory must sign in once and assume permissions in many member accounts. The company wants permission sets mapped to groups rather than an IAM user in each account. Amazon Cognito is reserved for the consumer mobile app, not for staff. Which solution will meet these requirements?
Answer: B. Workforce SSO plus permission sets is IAM Identity Center. Cognito is customer identity; per-account IAM users recreate long-lived humans.

Good to know: Cognito would be correct for application customer sign-up and sign-in. IAM users would appear if the stem still required long-lived console users and forbade Identity Center.
Q12A consumer mobile application needs sign-up, sign-in, and user profiles for millions of customers who are not employees. Staff will continue to use workforce federation for the AWS Management Console. The identity service must be application identity, not IAM users for each customer. Permission sets stay reserved for employees. Which solution will meet these requirements?
Answer: D. Customer and application identity is Amazon Cognito. Identity Center is workforce SSO; IAM users and SCPs are not a customer directory.

Good to know: IAM Identity Center would be the answer for employees assuming roles in AWS accounts. This item does not ask for an API Gateway authorizer.
Q13A new AWS account’s root user still has an access key from a proof of concept. Finance uses root for daily billing clicks. Security wants root used only for the few tasks that require it, with no standing access keys. Workforce users should have their own identities for routine work. Which solution will meet these requirements?
Answer: A. Protect root by removing standing keys and keeping it off routine tasks. Daily work belongs on IAM or Identity Center identities.

Good to know: Enabling MFA on root is the usual companion control and would be required if the stem stressed a second factor. SCPs do not grant root extra power in that way.
Q14Privileged humans sign in to the AWS Management Console with IAM users that still have only a password. Security requires a second factor before those users can perform administration. Workloads on Amazon EC2 must keep using roles, not human passwords. The company will not share the account root user. Which solution will meet these requirements?
Answer: C. MFA is the second factor for privileged human console access. EC2 should keep instance roles; Cognito is not the workforce console path taught here.

Good to know: Identity Center can also enforce MFA for workforce SSO. Access keys in AMIs would violate the workload-role rule. Root sharing increases blast radius.
Q15An application role currently has AdministratorAccess so developers can move quickly. The role only needs s3:GetObject on one bucket and dynamodb:PutItem on one table. Security wants the identity policy narrowed to those actions. An SCP already allows those services in the OU and must not be treated as the grant. Which solution will meet these requirements?
Answer: B. Least privilege is an identity policy that allows only the needed actions. The SCP already leaves room; it does not grant those actions by itself.

Good to know: Relying on the SCP alone would be correct only if SCPs granted access, which they do not. A second admin policy would widen, not narrow, the role.
Q16Developers in a member account cannot read a logging bucket even though an SCP on their OU allows s3:GetObject. The SCP must remain a guardrail and must not be treated as the grant. Shared access keys are forbidden. The bucket is in the same account as the developers. Which solution will meet these requirements?
Answer: D. The SCP already leaves room for S3 reads; an identity (or resource) allow is still required. A second SCP cannot grant the permission.

Good to know: If the SCP denied S3, you would first open room in the SCP and then add the identity allow. Cognito does not change SCP evaluation.
Q17Security must attach one guardrail that covers all production member accounts but not sandbox accounts. The company already uses AWS Organizations. Sandbox teams must keep experimenting in a separate OU from production. Workload IAM policies in production should still grant only what each role needs. Which solution will meet these requirements?
Answer: A. OUs group accounts so an SCP can cap production without constraining sandbox. SCPs attach to the organization tree, not to individual IAM users as the primary pattern.

Good to know: Attaching the SCP to sandbox as well would freeze experiments. IAM users in the management account would mix blast radius rather than apply an OU guardrail.
Q18A CI pipeline currently uses a 90-day IAM user access key stored in a vault. Security wants the pipeline to obtain short-lived credentials by assuming a role instead. The pipeline is not a customer-facing mobile app. The company will not put root keys in the pipeline. Which solution will meet these requirements?
Answer: C. Pipelines should assume a role for temporary STS credentials instead of long-lived user keys. Cognito is customer identity, not this machine path.

Good to know: An IAM user key would remain only if the stem still required a long-lived principal and forbade roles. Identity Center is for workforce users, not typical CI machine identity.
Q19An Amazon EC2 fleet must read from Amazon S3. Security forbids access keys in AMIs, user data, or local disk. Temporary credentials must come from the instance. An SCP already allows S3 in the OU and must not be treated as the grant. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and C. The role holds the identity allow and the instance profile delivers it to EC2. The SCP only leaves room; it does not grant.

Good to know: Keys in the AMI would be the anti-pattern if long-lived secrets were allowed. A resource policy on the bucket could add who may access, but the instances still need a role.
Q20An application in Account A needs GetObject on a bucket in Account B. Long-lived keys must not be shared. Account B will host the credentials the application uses. The teams will not make the bucket public, and an SCP must not be used as the grant. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and D. Cross-account temporary access is a role in the resource account plus a trust policy that lets Account A assume it. SCPs and public buckets are the wrong grants.

Good to know: A bucket policy that allows a principal still in Account A is the resource-policy alternative when the app does not assume a role in B.
Q21Developers in a member account must read objects in that account’s S3 bucket. An SCP on their OU currently denies all S3 actions. Security will not use the SCP as a grant and will not share access keys. The bucket remains private. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: C and E. Effective access needs SCP room and an identity allow. Opening the SCP without an IAM allow still fails; an IAM allow under a deny SCP still fails.

Good to know: If the SCP already allowed S3, only the identity policy would still be missing. MFA does not override an SCP deny.
Q22A company wants employees to use one workforce sign-in to reach multiple member accounts. Each department needs different AWS permissions. Customer mobile sign-in is out of scope. The company will not create an IAM user in every account for each employee. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and E. Identity Center provides the workforce SSO plane; permission sets map groups onto account roles. Cognito is the customer-identity choice.

Good to know: Cognito would be correct for app customer sign-up. Per-account IAM users would be the long-lived alternative the stem rejected.
Q23Developers may create application roles but must not attach policies beyond a security-approved ceiling, and they must not pass arbitrary roles to Amazon EC2. An OU-wide SCP is considered too coarse for this per-role limit. Long-lived access keys are not an acceptable substitute. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: B and C. The permissions boundary caps what a delegated role can become. Scoped PassRole stops developers from attaching other roles to EC2.

Good to know: An SCP would be the answer for an OU-wide service or Region guardrail. AdministratorAccess on created roles would ignore the ceiling.
Q24A new production account still uses the root user for daily console work and has no MFA on root. Security wants root reserved for rare account-recovery tasks and a second factor on that user. Workforce identities should handle daily administration. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: D and E. Root protection is MFA plus not using root for routine work. Daily administration belongs on least-privilege workforce identities.

Good to know: More root access keys would increase standing secret risk. MFA on privileged IAM users is also good practice but is a different control than protecting root.
Q25A company wants production compute in one account and a shared networking resource in a network account to reduce blast radius. The compute account must use the shared resource without duplicating it. The company already uses AWS Organizations. Customer identity services are out of scope. Which combination of steps should a solutions architect take? (Select TWO.)
Answer: A and B. Separate accounts cut blast radius; RAM shares supported resources such as networking constructs without copying them. Cognito does not share VPCs.

Good to know: A single account with IAM users would be simpler operations but would not meet the blast-radius constraint. SCPs would cap those accounts; they would not share the subnet.
